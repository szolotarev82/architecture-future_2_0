# Задание 3. Разработка технологического радара и роадмапа изменений для поддержки бизнес-целей компании «Будущее 2.0»

## 1. Технологический радар

Интерактивный технологический радар на базе `aoe_technology_radar` (Node.js) расположен в директории [`./tech-radar/`](./tech-radar/).

* **Запуск локально:** `cd tech-radar && npm install && npm run serve` (радар откроется по адресу `http://localhost:3000/techradar`).
* В карточках технологий (`./tech-radar/radar/2026-11-14/*.md`) отражены текущие легаси-системы (кольцо **Hold**), пилотные инструменты (**Trial**), перспективные технологии для партнёров (**Assess**) и целевой облачный стек (**Adopt**) с указанием поддерживаемых бизнес-сценариев.

## 3. Бизнес-обоснование планируемых изменений

Каждый этап роадмапа напрямую влияет на ключевые бизнес-показатели «Будущего 2.0»:

### 1. Обоснование Этапа 1 (Облачный фундамент, Terraform и изоляция медкарт)

* **Качество и безопасность сервиса.** Исключение медкарт и историй болезней из аналитического контура защищает компанию от критических штрафов за нарушение врачебной тайны и 152-ФЗ, а разделение сети на публичную и приватную подсети закрывает прямые атаки на базы данных.
* **Возможности масштабирования.** Использование подхода Infrastructure as Code (Terraform) позволяет за считанные минуты клонировать изолированные облачные среды под новые бизнес-направления без ручной настройки серверов.

### 2. Обоснование Этапа 2 (Запуск Data Lakehouse, Kafka и вынос логики Финтеха)

* **Скорость принятия решений и Time-to-Market.** Вынос банковской логики из монолитного DWH в независимые сервисы позволяет финтех-подразделению запускать новые кредитные и платёжные продукты за недели вместо месяцев, не дожидаясь правок в общем хранилище.
* **Качество финансовых сервисов.** Замена устаревшей шины ESB на распределённый брокер **Apache Kafka** устраняет единую точку отказа и гарантирует стабильную обработку транзакций даже при пиковых нагрузках в клиниках.
* **Снижение затрат.** Хранение сотен терабайт исторических данных в объектном хранилище **S3 + Apache Iceberg** обходится в разы дешевле, чем масштабирование проприетарного SQL Server.

### 3. Обоснование Этапа 3 (Внедрение DataHub, Apache Superset и автономия ИИ)

* **Скорость принятия управленческих решений.** Переход на колоночную СУБД **ClickHouse** и портал **Apache Superset** сокращает время формирования сложных отчётов с часов до нескольких секунд. Руководители и бизнес-пользователи сами строят нужные срезы в реальном времени без очереди к ИТ-отделу.
* **Качество медицинских услуг.** Прямой обмен обезличенными снимками между клиниками и ИИ-сервисами (`gRPC`) обеспечивает врачам мгновенные диагностические подсказки во время приёма пациента.
* **Снижение затрат и рисков.** Каталог **DataHub** автоматизирует контроль прав доступа (RBAC) и прозрачность данных (Data Lineage), снижая трудозатраты аналитиков на поиск нужных таблиц и проверку достоверности цифр.

### 4. Обоснование Этапа 4 (API для партнёров, георезервирование и вывод легаси)

* **Масштабирование бизнеса (M&A и партнёрства).** Стандартизированные контракты событий в **Kafka** и шлюз **Kong** позволяют подключать фармацевтические компании и производителей медицинского оборудования по модели *Plug & Play* без перестройки ядра системы.
* **Снижение операционных затрат (TCO).** Отключение устаревшего MS SQL Server 2008 и шины Apache Camel избавляет компанию от расходов на поддержку неподдерживаемого оборудования и поиск дефицитных специалистов по легаси-стеку (при этом в клиниках легаси-интерфейс PowerBuilder выводится плавно и без остановки приёма пациентов).
