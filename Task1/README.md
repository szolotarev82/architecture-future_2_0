# Задание 1. Проектирование целевой архитектуры и приоритизация проблем для поддержки ключевых бизнес-сценариев компании «Будущее 2.0»

## 1. Целевая архитектура системы (через 1 год)

Целевая архитектура строится в облачной инфраструктуре (**Yandex Cloud**) на базе принципов **Data Mesh** (доменно-ориентированная архитектура данных), **Data Lakehouse** и **Event-Driven Architecture** (событийно-ориентированный обмен данными).

### Ключевые архитектурные решения

* **Декомпозиция монолита DWH.** Бизнес-логика выносится из устаревшего MS SQL Server 2008 в независимые сервисы доменов (Клиники, Финтех, ИИ).
* **Строгая изоляция медицинских данных.** Медицинские карты, истории болезней и результаты диагностических исследований хранятся в закрытом медицинском контуре (`PostgreSQL + S3`) и физически не попадают в аналитический слой.
* **Событийная шина вместо ESB.** Устаревшая шина Apache Camel заменяется на распределенный брокер сообщений **Apache Kafka** для асинхронного обмена событиями между доменами.
* **Data Lakehouse и Data Governance.** Холодные исторические данные и обезличенные датасеты для ML хранятся в **Data Lake (Yandex Object Storage S3 + Apache Iceberg)**, а быстрые витрины для отчетов — в колоночной СУБД **ClickHouse**. Оркестрацию миграции из легаси и пересчет витрин выполняет **Apache Airflow**, управление метаданными, прослеживаемостью (Data Lineage) и правами доступа — **DataHub**, а визуализацию — **Apache Superset**.

### Диаграмма контейнеров (модель C4)

Исходный код диаграммы находится в файле [`c4_container.puml`](./c4_container.puml).

### Как целевая архитектура поддерживает ключевые бизнес-сценарии

* **Быстрая отчетность и Self-Service BI.** Связка **ClickHouse** и **Apache Superset** под управлением каталога **DataHub** сокращает время построения отчетов с часов до секунд. Сотрудники самостоятельно конструируют нужные срезы в пределах своих прав доступа (RBAC/ABAC).
* **Безопасность и соблюдение требований регуляторов.** Медицинские карты, истории болезней и результаты исследований строго изолированы в медицинском хранилище и не попадают в Data Lake или витрины. Оперативная ИИ-диагностика снимков идет напрямую из сервисов клиники по защищенному каналу `gRPC`.
* **Независимое развитие финтех- и ИИ-направлений.** Каждый домен владеет своими сервисами и базами данных. Банковское и ИИ-подразделения могут выпускать обновления без изменений в общем хранилище и без влияния на работу клиник.
* **Поддержка ML и больших объемов данных.** Архитектура **Data Lakehouse** позволяет экономично хранить сотни терабайт исторических данных в **S3 + Apache Iceberg** для обучения моделей ИИ, не перегружая быстрый аналитический слой ClickHouse.
* **Масштабирование в перспективе (фармацевтика и производители электроники).** Новые партнеры подключаются как автономные домены через единый шлюз безопасности (**Kong / Keycloak**) и событийную шину (**Kafka**). Фармкомпании передают данные о поставках и остатках лекарств, производители электроники — телеметрию медицинского оборудования, а облачная инфраструктура (IaC / Terraform) позволяет за минуты развернуть для них изолированные среды по готовому шаблону.

## 2. Проблемные места текущей архитектуры (As-Is) и влияние на бизнес

| Проблема в текущей системе | Техническая суть проблемы | Пострадавшие бизнес-сценарии и последствия |
| :--- | :--- | :--- |
| **Устаревший монолитный DWH (MS SQL 2008)** | Хранение сотен терабайт разнородных данных в одной старой БД, поддержка которой прекращена производителем (отсутствуют патчи безопасности). | **Скорость решений и безопасность.** Сложные отчеты строятся часами, руководство теряет оперативность. Критический риск взлома и утечки медицинских и банковских данных. |
| **Бизнес-логика зашита внутри DWH** | Правила расчетов для клиник, банка и ИИ реализованы внутри хранимых процедур и ETL-процессов общего хранилища. | **Вывод новых продуктов (Time-to-Market).** Доработки в одном направлении создают узкое горлышко, конфликты команд и тормозят релизы в других. |
| **Медкарты лежат вместе с аналитикой** | Истории болезней и результаты исследований хранятся в том же DWH, откуда строятся BI-отчеты. | **Соблюдение закона и запуск Self-Service BI.** Нельзя открыть конструктор отчетов для сотрудников из-за риска нарушить врачебную тайну и 152-ФЗ. |
| **Старая шина ESB (Apache Camel)** | Централизованная шина со сложной жесткой маршрутизацией и единой точкой отказа. | **Подключение новых партнеров (Фарма, Электроника).** Интеграция каждого нового направления требует трудоемких переделок шины. |
| **Легаси-интерфейс на PowerBuilder** | Морально устаревшее десктоп-приложение для операторов в клиниках. | **Качество медицинского сервиса.** Врачам неудобно работать с современными ИИ-подсказками, сложно развивать интерфейс и искать специалистов для поддержки. |

## 3. Приоритизация выявленных проблем (MoSCoW + Матрица Эйзенхауэра)

| Проблема | Метод MoSCoW | Матрица Эйзенхауэра | Связь с целями бизнеса |
| :--- | :--- | :--- | :--- |
| **Изолировать медкарты и исследования от аналитики** | **Must Have** | **Важно и Срочно** | **Безопасность и закон.** Без физического разделения данных невозможно запускать портал самообслуживания из-за риска утечки врачебной тайны и штрафов. |
| **Уйти от MS SQL 2008 в облачный Data Lakehouse** | **Must Have** | **Важно и Срочно** | **Выручка и скорость решений.** Закрывает критические уязвимости безопасности, решает проблему сотен терабайт данных и ускоряет отчеты с часов до секунд. |
| **Вынести бизнес-логику из DWH в домены** | **Must Have** | **Важно, но не Срочно** | **Time-to-Market.** Позволяет банку и ИИ-сервисам быстро запускать новые продукты и растить выручку независимо друг от друга. |
| **Запустить Self-Service BI (Superset) и DataHub** | **Must Have** | **Важно, но не Срочно** | **Прямая цель руководства.** Дает сотрудникам удобный конструктор отчетов с прозрачным управлением правами доступа и Data Lineage. |
| **Заменить шину ESB на Apache Kafka и API Gateway** | **Should Have** | **Важно, но не Срочно** | **Масштабирование бизнеса.** Упростит и ускорит подключение фармацевтических компаний и производителей электроники в будущем. |
| **Заменить интерфейс на PowerBuilder** | **Could Have** | **Не Важно, но Срочно** | **Качество сервиса в клиниках.** Улучшит работу врачей, но руководство разрешило временно оставить легаси в первый год трансформации. |
